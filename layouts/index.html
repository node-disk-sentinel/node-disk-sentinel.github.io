Frequently Asked Questions

Common questions about architecture, RAID controllers, and hardware telemetry.

Can I monitor disks behind a Hardware RAID controller?

Node Disk Sentinel maintains a strict 1:1 mapping with OS block devices (/dev/sd*, /dev/nvme*n*). Hardware RAID controllers (HPE Smart Array, MegaRAID, Dell PERC) combine drives into virtual logical volumes, hiding physical disks from the operating system and causing smartctl collection errors (e.g. requires option '-d cciss,N').

We strongly recommend configuring storage controllers in HBA / IT / Pass-Through mode (standard for Kubernetes, Ceph, and Longhorn) so each physical drive is exposed directly to the OS and monitored individually. Alternatively, virtual volumes can be excluded via discovery.exclude.

How do I exclude virtual volumes or specific disks?

Configure discovery.exclude in Helm values.yaml with comma-separated exact matches, for example - "vendor=HP,model=LOGICAL_VOLUME" or - "name=sdn".

Excluded devices are neither probed nor published as PhysicalDisk resources, and any matching existing resources are automatically deleted during the next scan.

Why do SAS disks show fewer telemetry fields than SATA or NVMe?

Telemetry attributes like reallocatedSectors (ATA 5) and pendingSectors (ATA 197) are ATA-specific, while percentageUsed and mediaErrors are NVMe-specific.

Enterprise SAS drives do not expose ATA attributes. Their health is evaluated via SCSI Primary Commands error counter logs and grown defect lists. Fields that do not apply to the hardware protocol are omitted (omitempty) in the resource YAML.

Can I manually create PhysicalDisk resources?

No. Node Disk Sentinel continuously reconciles PhysicalDisk resources against the node's local udev hardware inventory. Any resource without a corresponding physical block device on the host is flagged as DiskMissing.

How does Node Disk Sentinel identify disks across reboots?

Kernel device letters (/dev/sda, /dev/sdb) are dynamic and can swap across reboots or bus rescans. Node Disk Sentinel resolves this through predictable device names and paths:

Device paths (status.info.path) follow a strict hierarchy of persistent udev symlinks: WWN (/dev/disk/by-id/wwn-*), NVMe EUI, model/serial, and PCIe bus topology (/dev/disk/by-path/*). Furthermore, Kubernetes PhysicalDisk resource names are derived deterministically from hardware identifiers, ensuring metric labels and alerting rules survive reboots and controller resets.
